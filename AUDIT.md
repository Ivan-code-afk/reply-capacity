## Расчёты

- Вместимость: целая часть отношения ежедневного времени ко времени одного ответа.
- Ответов за день: минимум вместимости и доступной очереди с новыми сообщениями.
- Остаток: предыдущая очередь + входящие − ответы; отрицательные значения исключены.
- Необходимая ежедневная вместимость: входящие + округлённая вверх доля старой очереди за выбранный период.
- Дополнительное ежедневное время: максимум нуля и разности необходимого и доступного бюджета.

При постоянном входящем потоке остаток независимо проверяется формулой `max(0, initial + days * (incoming - capacity))`. Минимальность требуемого времени проверена: его достаточно, а при уменьшении положительного требуемого бюджета на одну минуту очередь не успевает исчезнуть. Проверка охватывает 3 360 сочетаний, включая максимальные допустимые значения ядра и периоды 1, 2, 7 и 365 дней.

Контрольные примеры:

| Входящие / очередь / мин. на ответ / мин. в день | Вместимость | Ответы за 7 дней | Остаток | Доп. мин. в день |
| --- | ---: | ---: | ---: | ---: |
| 20 / 35 / 4 / 60 | 15 | 105 | 70 | 40 |
| 3 / 2 / 5 / 0 | 0 | 0 | 23 | 20 |
| 0 / 0 / 2 / 0 | 0 | 0 | 0 | 0 |
| 2 / 0 / 10 / 9 | 0 | 0 | 14 | 11 |

Расчётных ошибок не обнаружено. Нулевая длительность ответа запрещена; нулевая очередь, входящие и бюджет допустимы. Дробные, нечисловые, бесконечные и выходящие за границы значения отвергаются ядром. Требуемое время может математически превышать 24 часа: это результат модели, а не допустимый ввод ежедневного бюджета.

## Исправленные проблемы

1. Поле ежедневного времени допускало целые минуты, а ползунок имел шаг 5. При вводе 61 минуты браузер мог показывать на ползунке 60. Шаг приведён к одной минуте.
2. При нечисловом неограниченном значении обработчик оставлял поле без синхронизации с последним принятым состоянием. Теперь поле восстанавливается. Браузерная нормализация пустого поля также сохраняет последнее значение.
3. При высокой нагрузке рекомендация обещала разгрузку с бюджетом свыше 24 часов в сутки. Теперь интерфейс и копируемый результат явно сообщают о невозможности такого сценария для одного человека. Математическая потребность во времени не обрезается.

## Готовность к публикации

Проект подготовлен как статический сайт без сборки. CI запускает оба набора тестов. Окончательный результат Actions для последнего коммита указан в PR.

Перед публикацией необходимы ручная проверка мобильного и настольного интерфейса, открытие `index.html` напрямую, проверка консоли/сети и явное решение владельца о слиянии и публикации. После разрешённого слияния можно включить GitHub Pages из `main` и `/(root)`; в текущем состоянии сайт не публиковался. Подтверждённых неисправленных ошибок ядра нет; ограничения браузерной проверки остаются открытыми.

## Обновление: мобильная версия и четыре языка

В той же ветке PR №1 реализован переключатель `EN | RU | FR | DE` без флагов и внешних сервисов. Первое посещение всегда английское; недопустимый сохранённый язык также заменяется английским. Язык хранится в `reply-capacity-language`, отдельно от числовых параметров в прежнем ключе `reply-capacity-v1`. Переключение не меняет входы или результаты; сброс не меняет язык. Сохраняется работа при отказе localStorage.

Локализация вынесена в простой встроенный словарь `reply-capacity-i18n.js`; код взаимодействия со страницей перенесён из inline-скрипта в `reply-capacity-ui.js`. Переведены все статические и динамические тексты, метаданные, подписи SVG, ARIA, состояния, уведомления, единицы, предупреждения и копируемые отчёты. Числа и формы существительных используют Intl.NumberFormat/Intl.PluralRules. Кнопки языков имеют стандартное клавиатурное поведение, переведённые доступные имена и aria-pressed; выбранный язык визуально выделен. Атрибут html lang и title меняются сразу. Состояния уведомлений сброса и копирования также переводятся при смене языка.

Для узкой сетки используется `minmax(0,1fr)`, карточки имеют `min-width:0`, заголовки переносятся. Длинные переводы, метрики, число с единицей, шапка и кнопки могут переноситься без обрезания содержимого. Горизонтальное переполнение не маскируется через `overflow-x:hidden`.

Ядро `reply-capacity-core.js` и `test-core.js` не изменены относительно предыдущего аудита: 19/19 тестов, включая 3 360 сценариев. В `test-ui.js` добавлены проверки четырёх одинаковых наборов ключей и параметров шаблонов, отсутствия русских строк в остальных языках, склонений, сохранения/восстановления языка, сброса, всех состояний очереди и неизменности полных результатов при смене языка.

### Реальные браузерные проверки

Встроенный интерактивный браузер по-прежнему завершает навигацию тайм-аутом CDP. Вместо него в GitHub Actions добавлен запуск настоящего headless Chrome без зависимостей приложения:

- `tests/browser.html`: 5 ширин × 4 языка × 3 сценария = 60 сочетаний. Проверяются фактические scrollWidth/clientWidth и границы карточек, полей, ползунков, графика, кнопок и переключателя. На первом прогоне [run #6](https://github.com/Ivan-code-afk/reply-capacity/actions/runs/39628399392) все сочетания успешно прошли; например, на 320 px во всех языках scrollWidth/clientWidth = 320/320. Проверены нативный ползунок и восстановление языка/данных после реальной перезагрузки.
- Финальный workflow также проверяет ошибки выполнения обработчиков, отсутствие ресурсов стороннего origin и EN по умолчанию при запуске Chrome с `--lang=ru-RU`.
- `tests/prepare-file-smoke.js` создаёт временную копию четырёх файлов приложения с диагностическим скриптом. Chrome открывает её через `file://` и проверяет стартовый расчёт, EN по умолчанию, переключение языка без изменения результата и сброс с сохранением языка. Код приложения при этом не меняется. Итог финального прогона указан в PR.

Остаются ручная оценка внешнего вида, проверка настоящего скринридера, клавиатурного взаимодействия и буфера обмена, а также Safari/Firefox/реальные мобильные устройства. Измерения DOM в Chrome подтверждены, но не объявляются полноценной визуальной или кроссбраузерной проверкой. Слияние и публикация не выполнялись.
