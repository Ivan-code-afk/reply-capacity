## Расчёты

- Вместимость: целая часть отношения ежедневного времени ко времени одного ответа.
- Ответов за день: минимум вместимости и доступной очереди с новыми сообщениями.
- Остаток: предыдущая очередь + входящие − ответы; отрицательные значения исключены.
- Необходимая ежедневная вместимость: входящие + округлённая вверх доля старой очереди за выбранный период.
- Дополнительное ежедневное время: максимум нуля и разности необходимого и доступного бюджета.

При постоянном входящем потоке остаток независимо проверяется формулой `max(0, initial + days * (incoming - capacity))`. Минимальность требуемого времени проверена: его достаточно, а при уменьшении положительного требуемого бюджета на одну минуту очередь не успевает исчезнуть. Проверка охватывает 3 360 сочетаний, включая максимальные допустимые значения ядра и периоды 1, 2, 7 и 365 дней.

Контрольные примеры:

| Входящие / очередь / мин. на ответ / мин. в день | Вместимость | Ответы за 7 дней | Остаток | Доп. мин. в день |
| --- | ---: | ---: | ---: | ---: |
| 20 / 35 / 4 / 60 | 15 | 105 | 70 | 40 |
| 3 / 2 / 5 / 0 | 0 | 0 | 23 | 20 |
| 0 / 0 / 2 / 0 | 0 | 0 | 0 | 0 |
| 2 / 0 / 10 / 9 | 0 | 0 | 14 | 11 |

Расчётных ошибок не обнаружено. Нулевая длительность ответа запрещена; нулевая очередь, входящие и бюджет допустимы. Дробные, нечисловые, бесконечные и выходящие за границы значения отвергаются ядром. Требуемое время может математически превышать 24 часа: это результат модели, а не допустимый ввод ежедневного бюджета.

## Исправленные проблемы

1. Поле ежедневного времени допускало целые минуты, а ползунок имел шаг 5. При вводе 61 минуты браузер мог показывать на ползунке 60. Шаг приведён к одной минуте.
2. При нечисловом неограниченном значении обработчик оставлял поле без синхронизации с последним принятым состоянием. Теперь поле восстанавливается. Браузерная нормализация пустого поля также сохраняет последнее значение.
3. При высокой нагрузке рекомендация обещала разгрузку с бюджетом свыше 24 часов в сутки. Теперь интерфейс и копируемый результат явно сообщают о невозможности такого сценария для одного человека. Математическая потребность во времени не обрезается.

## Готовность к публикации

Проект подготовлен как статический сайт без сборки. CI запускает оба набора тестов. Окончательный результат Actions для последнего коммита указан в PR.

Перед публикацией необходимы ручная проверка мобильного и настольного интерфейса, открытие `index.html` напрямую, проверка консоли/сети и явное решение владельца о слиянии и публикации. После разрешённого слияния можно включить GitHub Pages из `main` и `/(root)`; в текущем состоянии сайт не публиковался. Подтверждённых неисправленных ошибок ядра нет; ограничения браузерной проверки остаются открытыми.
